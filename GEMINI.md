# Maya Engine Context

Maya is a C++20 engine under architectural redevelopment for realistic 3D games. The current platform is macOS/Metal with Objective-C++, GLFW, and CMake. See README.md for build options, lifecycle contracts, and known limitations.

Before implementing world, asset, simulation, or renderer changes, read [docs/architecture/README.md](docs/architecture/README.md) and its linked contracts from #990. They distinguish intended architecture from current APIs and leave product/platform/performance decisions explicitly open. Update the relevant record when changing a contract.

## Build and validation

```bash
cmake -S . -B build
cmake --build build -j 4
./build/maya_player
./build/maya_editor
./build/maya_sample
ctest --test-dir build -L cpu --output-on-failure
ctest --test-dir build -L gpu --output-on-failure
tools/check_milestone.sh build   # CPU, headless GPU, and windowed groups; logs in build/milestone-logs; exit 1 failed, 3 flaky
```

GPU tests require an interactive macOS session. Applications support `--smoke [positive frame count]`. Use `MAYA_ENABLE_SANITIZERS=ON` in a separate build directory for ASan/UBSan.

## Boundaries

- `MayaAssets` / `Maya::Assets`: Project catalog, typed asset handles, shared version leases, the initial OBJ/material/texture providers, and project files (`project.hpp`: content root, catalog, startup scene). See [docs/assets.md](docs/assets.md) for loading and GPU ownership boundaries. Resolve project content through `Project::resolve`, never the working directory or FileSystem search roots ([docs/projects.md](docs/projects.md)). Since #1062 loads are asynchronous ([docs/assets.md](docs/assets.md#asynchronous-loading)): providers `prepare` on a job (no device, no registry) and finalize on the owner thread in `AssetRegistry::update`. Frame code uses `try_acquire`, `request`, and streaming extraction (`AssetLoading::stream`) and never blocks; `acquire`, `reload`, and `wait` are explicit waits, allowed inside a frame only under `AssetRegistry::ExplicitWait` (an action the user asked for, or a play session's scripts and clips). `AssetLoadStats::waited_in_frames` must stay 0.
- `MayaJobs` / `Maya::Jobs` (#1061): the process's job system, `job_system()` ([docs/jobs.md](docs/jobs.md)): a frame tier (user-interactive) and a background tier (utility) of workers, jobs with dependencies, cooperative cancellation, failures as values, `parallel_for`, `JobScope`, and `CompletionQueue` for owner-thread results. Jobs never touch a World, the registry, or the GPU; owners scope their jobs and cancel them before they are destroyed. Physics and cooking run on it; never start raw `std::thread`s for engine work.
- `MayaTextures` / `Maya::Textures` (#1031): texture descriptors (`.texture`), Maya's own KTX2 reader and writer, cooking source images (stb_image, stb_image_resize2, astcenc; all three private to it), and (#1035) environment files (`.environment`) cooked from Radiance HDR images into irradiance coefficients, a prefiltered cube, and the split-sum table. MayaAssets links it to cook PNG and JPEG sources at load. See [docs/assets.md](docs/assets.md#textures). Normal maps are stored as x in RGB and y in alpha; never write a KTX2 subset beyond what `ktx validate` accepts (`maya_ktx2_validate` with `MAYA_KTX_TOOL`).
- `MayaImport` / `Maya::Import` (#1036): `import_gltf` imports glTF files into a project: catalog entries for their meshes and textures as parts of the source (`models/helmet.glb#mesh/0/0`), a material file per glTF material, a scene file, and an import file (`<source>.import`) holding the settings and the IDs given, by identity, so a reimport keeps them. The reader is `GltfFile` (`gltf.hpp`, in MayaAssets); only `gltf.cpp` includes cgltf, and every problem names its JSON path. Write the catalog last, and leave it unchanged when an import fails; never overwrite a material or scene file whose text no longer has the hash the import recorded. See [docs/import.md](docs/import.md).
- Skeletal animation (#1038, [docs/animation.md](docs/animation.md)): skins and clips (`animation.hpp`: `SkinAsset`, `AnimationAsset`, glTF's samplers, and their cooked forms; in MayaWorld) are catalog parts of imported glTF files (`skin/<s>`, `animation/<a>`). Joints are entities: `maya.animation`'s clip names them, and `maya.skin`'s skin, by **name path** below an entity (`name_path.hpp`), so renaming a joint unbinds it, which must be reported, never silent. The animation system (`simulation/animation.hpp`) is the last of `play_systems`; it writes joints' transforms through the tick's commands, so presentation, replay, and Stop need nothing extra, and lists jumps in `TickContext::jumps`. Cache bindings only while `World::names_revision()` is unchanged. Skinning is on the GPU (`SkinVertex` stream at buffer 5, the frame's joints at buffer 6, `DrawConstants::skin`); keep `litSkinnedVertex`/`shadowSkinnedVertex` in step with their unskinned twins. `animation_samples_tests.cpp` checks poses against an independent cgltf evaluator: never weaken its tolerance to make a change pass.
- The cook cache (#1036, `cook_cache.hpp`, [docs/assets.md](docs/assets.md#cook-cache)): `FileAssetProvider` reads cooked textures, environments, and imported meshes, textures, skins, and clips from `<project folder>/.maya/cache`, keyed by SHA-256 of the sources and settings. Raise the kind's cook version (`texture_cook_version`, ...) whenever a change to cooking changes its bytes, and keep cooking deterministic (the `import` benchmark workload and `cook_cache_tests.cpp` check it). An imported part's key must cover every file its source names.
- `MayaWorld` / `Maya::World`: CPU-only entity identity, packed component storage, and atomic structural command batches. No RHI, window, or editor dependency. See [docs/world.md](docs/world.md) for APIs and scoped-borrow rules.
- Coordinates (#1065, [contract](docs/architecture/runtime-world-contracts.md#coordinates)): world positions are double (`math::DVec3`; world poses are `math::Affine`, a float 3×3 and a double translation; Jolt is built with `JPH_DOUBLE_PRECISION`). Never narrow a world position to float except relative to an origin near it: render snapshots and views are camera-relative (`RenderExtractOptions::origin` is the view camera's position; `view_frame`), debug draws have an `origin`, physics converts at `jolt_position`/`maya_position`, and scripts get a Luau `position` type. Offsets between positions are float (`(a - b).to_float()`). Check precision far out with the origin-offset sweep (`[precision]` tests, to 100 km).
- Worlds (#1064, [docs/world.md](docs/world.md#worlds-and-cells)): a `.world` file, a persistent scene, and a scene per 128 m cell (`world_io.hpp`), cooked to packed binary (`scene_binary.hpp`); `MayaStreaming`'s `WorldStreamer` loads cells on jobs and activates them under World stage groups (`create_staged`, `publish`, `stage`, `discard`) within a 1 ms frame budget, starting each step only when its measured cost fits. Never make a cell's entities visible piecemeal, scan every entity or body per tick (use `WorldCommitResult::destroyed` and the transform and edit journals), or let a reference pin a cell (references are weak, by EntityId).
- Residency (#1063, [docs/assets.md](docs/assets.md#residency)): resident bytes are kept by category (`residency.hpp`), under budgets from the project (W1's by default); `AssetRegistry::update` releases unleased versions over budget, least recently used first, a bounded number an update, never one leased or used since the last update. Never release what something leases; never make a frame hold a lease it does not need (it pins content: the Assets panel shows thumbnails without leasing). New resident content must be counted in its category, and a change to how something cooks must keep `AssetCooker::cook_key` (what pruning keeps) and cooking on the same key functions.
- `MayaScene` / `Maya::Scene`: Versioned scene files, detached scene documents, validated loading into a new World, and atomic saves. Links only MayaWorld; asset references are checked through `asset_property_context(registry)`. Added properties migrate by `PropertyDescriptor::since`; a reinterpreted one needs a step in the codec's `migrate` (the first: `maya.light` 1 to 2, lumens to candela, #1034; `maya.transform` 1 to 2 reads version-1 translations as floats, #1065). See [docs/scene.md](docs/scene.md#versions-and-migration).
- `MayaRHI` / `Maya::RHI`: GraphicsDevice validation, per-session handles, deferred retirement, and `NullGraphicsDevice` for CPU tests. The Metal backend lives in MayaRuntime. See [docs/rhi.md](docs/rhi.md).
- `MayaRenderer` / `Maya::Renderer`: Render snapshot extraction from a World, camera views, offscreen targets (HDR scene color, depth, and tone-mapped color), the lit, tone-map, and debug passes, and presentation into a window or panel. Scene light is HDR; only the tone-map pass turns it into display values, with the camera's EV100 exposure and AgX or PBR Neutral ([docs/renderer.md](docs/renderer.md#exposure-and-tone-mapping)). Surfaces shade with glTF's metallic-roughness model and texture maps ([docs/renderer.md](docs/renderer.md#materials)); keep `tests/support/shading.hpp` in step with `litFragment` (light from the surroundings is the Sample Viewer's form since #1036, and `sample_viewer_tests.cpp` compares it with Khronos's renders, recaptured only with `tools/sample_viewer/capture.sh` and the owner's approval), and remember a directional light's intensity is illuminance in lux (a white diffuse surface shows intensity / π) and a point or spot light's is candela (#1034). Each view draws at most 16 point and spot lights, chosen by `plan_lights` (`light_plan.hpp`), and reports the rest in `Renderer::last_lights()`; never drop a light silently. Shadows ([docs/renderer.md](docs/renderer.md#shadows)): the sun's four cascades and up to four spot maps, rendered before the view; keep cascades stable (spheres of fixed size, centres snapped to whole texels) and test bias changes against the acne, contact, cascade-edge, and shimmer cases in `lighting_gpu_tests.cpp`. Debug views (#1037, `RenderView::debug_view`) live in `litFragment` only under `#ifdef MAYA_DEBUG_VIEWS`, compiled into separate "(debug view)" pipelines when a view is chosen; keep the lit path free of them, and add a view to `DebugView`, its name list, the eye menu, and the debug-view references together. A scene's `maya.environment` component lights it with image-based lighting and draws the sky ([docs/renderer.md](docs/renderer.md#environments)); environments are cooked on the CPU when they load (`environment_cook.hpp`, in `MayaTextures`), never per frame, and the shader's `equirect_uv`, `to_environment`, and spherical-harmonic basis must match the C++ ones. Reads Worlds; never edits them. See [docs/renderer.md](docs/renderer.md).
- `MayaRuntime`: Engine session lifecycle, existing core utilities, and graphics backend. No editor, sample, GLFW, or desktop-loop dependency.
- `MayaDesktop`: Window ownership, event loop, input events and window metrics, cursor capture, clipboard, cursor, and close-request services, window closes the application can defer (`Application::on_close_requested`), framebuffer resize, and CLI launch handling.
- `MayaEditor`: Editor shell on Dear ImGui (`MayaImGui`, editor-only): docked hierarchy/viewport/inspector/assets/diagnostics panels, an editor camera, and UI/viewport input routing. See [docs/editor.md](docs/editor.md). `SceneEditor` owns the open scene's World; make every editor change through it so it is undoable ([docs/editing.md](docs/editing.md)). Edits are recorded as before/after records of the touched entities only; never keep runtime handles in history. Continuous controls (drags, gizmos) wrap their frames in `begin_group`/`end_group`; typed values apply when entry ends ([docs/inspector.md](docs/inspector.md)). ImGuizmo (MIT) is editor-only and pinned to `22a6c900`. Projects, scene open/save, the unsaved-changes prompt, and the Assets panel are in `project_files.cpp` ([docs/projects.md](docs/projects.md)); ask before replacing a dirty scene (`request_open_scene`, `request_new_scene`, `request_close`). Play mode is in `play_mode.cpp`: it locks the SceneEditor and runs a separate `PlaySession`; the input router's third owner is the game.
- `MayaImGui`: Dear ImGui core sources, fetched only with `MAYA_BUILD_EDITOR`. Runtime, desktop, player, and sample must never link it; the `*_no_editor_ui` CTest checks enforce this.
- `MayaSimulation` / `Maya::Simulation`: Play sessions: the fixed clock, gameplay input frames, ordered `SimulationSystem`s, and the session's physics world, on a World built from a scene document. CPU-only; shared by the player and editor play ([docs/play.md](docs/play.md)). Gameplay writes go through the tick's commands; never touch the authored scene from play.
- `MayaMetrics` / `Maya::Metrics`: Nearest-rank summaries, sample windows, `Stopwatch`, and `FrameTiming`. CPU-only. Engine reports `FrameTiming` to `Application::on_frame_timing`.
- `maya_package` (`MayaPackage`, `src/maya/package/packager.cpp`, #1039): packages a project's scenes and exactly the assets they reach, cooked by `AssetCooker` (`asset_cooker.hpp`), into a macOS bundle with the player and its shader ([docs/projects.md](docs/projects.md#packages)). A packaged player resolves files only from its bundle (`FileSystem::package_resources`) and loads only cooked files (`PackageAssetProvider`, `package.hpp`). Keep packages repeatable (no times, sorted files) and refuse missing content at packaging, never at run time; a source format the cooker reads must also be packaged cooked.
- `maya_benchmark` (`MayaBenchmark`, `apps/benchmark/`): headless benchmark runner for `benchmarks/*.benchmark` manifests; JSON results with raw samples ([docs/performance.md](docs/performance.md)). `present on` opens a window and measures display pacing (#1026); compare presenting runs only with presenting runs. Report measured values as observations; never invent budgets. Keep tracked bytes and platform-reported memory apart; GPU time, per frame and per pass, comes only from `take_gpu_timings()`. Give new render passes a `RenderPassDesc::label`: it names their GPU time in the editor and in results. The `import` workload (`import_workload.cpp`, `r1_import.benchmark`) imports models and loads them cold and warm (#1036). Generated scenes' sun casts no shadows, so I1 and L1 compare across milestones; `lights.benchmark` measures lights and shadows (#1034). The `animation` workload (A1, `animation_workload.cpp`, #1038) plays copies of an imported skinned model and records each play system's time per tick; `a1_unskinned.benchmark` is its unskinned twin, for skinning's cost per pass. The `physics` workload (P1, `physics_workload.cpp`) is headless; changing its recipe makes a new version ([performance-baseline.md](docs/architecture/performance-baseline.md#p1-physics-stress)). Benchmark only on a cool machine.
- R1 (#1040, [docs/acceptance.md](docs/acceptance.md#r1)): `maya_r1` (`MayaR1`, `apps/r1/`) assembles the realistic reference environment from the fetched samples into a project (`build/r1` with RGBA8 for tests, through the `r1_project` CTest fixture; `build/r1-astc` for the benchmark), keeping IDs and the cook cache when run again. Change the recipe only with the owner's approval and a new `recipe_version`; the R1 references in `tests/references/r1` need re-approval when anything visible changes. The #1030 prototypes are gone. The world-scale prototypes (#1060, `prototypes/world`, [record](docs/architecture/world-scale-decision.md)) build with `-DMAYA_BUILD_PROTOTYPES=ON -DBUILD_TESTING=ON` in a Release scratch build (CTest label `prototype`); `tools/fetch_world_samples.sh` fetches W1's CC0 content into `build/world-samples`.
- Milestone acceptance ([docs/acceptance.md](docs/acceptance.md)): `tests/acceptance_tests.cpp` authors a project in `build/acceptance` that `maya_acceptance_player` runs with the real player, `tests/physics_acceptance_tests.cpp` does the same for milestone 2's reference interaction (`maya_physics_acceptance_player`), and `tests/content_acceptance_tests.cpp` for milestone 3's content workflow, which `maya_content_acceptance_package` packages and runs outside the checkout; V1 reference images live in `tests/references/v1` (re-bless with `MAYA_BLESS_REFERENCES=1` and inspect them before committing).
- `MayaPhysics` / `Maya::Physics`: Rigid bodies on Jolt Physics 5.6.0 ([docs/physics.md](docs/physics.md), [decision](docs/architecture/physics-scripting-decision.md)). A play session owns one `PhysicsWorld` and builds the scene's authored bodies at start, all or none; systems make requests through `TickContext::bodies` and read `TickContext::physics`. Only `src/maya/physics/` includes Jolt (`maya_library_headers` checks it); never expose Jolt types or body IDs. Physics writes kinematic and dynamic bodies' transforms: move them with forces, velocities, kinematic targets, or teleports, never `set_transform`. Jolt's hooks and types are process-wide; its jobs run on the job system's frame tier, and `set_physics_worker_threads` limits how many workers a step uses.
- Recording and replay (#1023, [docs/play.md](docs/play.md#recording-and-replay)): `PlayRecording` holds the tick-indexed input (`InputTrack`, changes only), seed, scene text, asset hashes, build (`maya/core/build_info.hpp`, in `MayaBuildInfo`), Jolt configuration, reloads, and a `state_hash` checkpoint every 60 ticks. `replay_refusal` refuses other builds, physics, changed assets, and reloads; never replay a refused recording. Anything new that affects the simulation must feed the state hash or the event/message trace, and replay tests must keep content free of `pairs` order over table, function, or userdata keys.
- Debug views (#1022, [docs/physics.md](docs/physics.md#debug-views), [docs/renderer.md](docs/renderer.md#debug-lines)): producers fill a `DebugDraw` (lines, x-ray lines drawn through surfaces (#1038, skeletons), and box/sphere/capsule outlines, `MayaWorld`), passed through `RenderExtractOptions::debug`; an empty one must cost nothing (no pipelines, uploads, or draws). Physics outlines come from collider descriptions (`play_physics_debug` from the physics world at shown poses, `authored_physics_debug` from components), not Jolt's `DebugRenderer`. Contacts and queries are captured only while `PhysicsWorld::set_debug_capture` is on, and capture must never change results. Editor preferences (`editor_preferences.hpp`) are per person, never in project files. The player draws debug views only with `--debug-physics` or `--debug-skeletons`.
- Presentation (#1016): play views draw `PlaySession::presentation()` (poses between the last two ticks, as `PresentationPoses`) through `RenderExtractOptions::poses` and `extract_render_view`. Phase 2 keeps each changed entity's previous local transform as the batch commits; teleports, reparenting, and spawns reset it. Presentation never writes the World; compose hierarchy from shown poses, never blend matrices.
- Physics events and queries (#1021): Jolt's contact listener only appends records; `PhysicsWorld::take_events` turns them into sorted per-pair events in phase 7, and systems read them in `SimulationSystem::late_fixed_update` (`TickContext::events`). Queries (`raycast`, `shape_cast`, `overlap`) run against the last completed step and sort by distance, then EntityId. Body requests made in phase 7 apply at the next step; never let phase 7 change the completed one.
- Scripting (in `MayaSimulation`, `src/maya/simulation/scripting/`): Luau 0.740 scripts attached by `maya.script` components ([docs/scripting.md](docs/scripting.md)). One sandboxed VM per play session with a memory limit and a deterministic work budget per hook call (a project file may set both: `script_work`, `script_memory`); `play_systems(sources, clips)` gives the built-in systems, the script system, and the animation system. Script changes go through the tick's commands and are validated like Inspector edits; a failing hook call is rolled back, reported through `PlayFrame::messages`, and stops only that instance. Only the scripting folder includes Luau (`maya_library_headers` checks it); never expose Luau types in public headers. The editor (`script_files.cpp`) watches script files, keeps each script's last good version for the Inspector and Play, and hands changed scripts to a playing session through `ScriptReloads`; the player never watches files.
- `MayaPlayer`: Runs a project's saved scene through a play session (`create_player_application`); the player and the sample both use it. No sample-specific C++: scene behavior is data (`maya.spin`, `maya.fly_control`, and scripts through `maya.script`).
- `apps/player/main.cpp`: Launches the player; takes an optional project and scene (a package: only one of its scenes), `--record file` or `--replay file`, `--debug-physics`, `--debug-skeletons`, and `--debug-view name`.
- `apps/editor/main.cpp`: Launches the editor; takes an optional project file or folder.
- `samples/basic_scene/main.cpp`: Launches the player on the sample project.

The host owns the window; Engine owns device and Application. Stop and destroy application content before device shutdown, then destroy the window. Shutdown is idempotent, startup failures roll back, and stopped engines can initialize a fresh session. Callbacks must not re-enter lifecycle methods.

`Mesh` and `Texture`/`Sampler` (`core/texture.hpp`) own the GPU resources behind MeshAsset and TextureAsset; the fly-camera `Camera` controller is a prototype utility retained pending its replacement issue; the legacy Scene and Material were removed by #998. Physics bodies come from `maya.collider`, `maya.rigid_body`, and `maya.physics_settings` components at Play start (#1019, `authored_physics`) or from code (#1017). Scripting is not implemented yet; only its #1015 prototypes exist.

World storage and the initial Name/Transform/MeshRenderer/Camera/Light schemas exist independently of those sample utilities. Structural edits use WorldCommands and explicit commit; never retain a component reference outside a query callback. Hierarchy and camera calculations are implemented; transform queries are read-only and edits use validated set_transform/reparent commands. Asset registry/residency services are implemented by #993. Shared [property metadata and validated edits](docs/properties.md) are implemented by #994; use this boundary for authoring/import/script values. Native non-transform component writes remain trusted. [Scene save/load](docs/scene.md) is implemented by #995: load into a separate World and replace the active one only on success. The [renderer](docs/renderer.md) (#998) extracts immutable snapshots from a World and renders camera views into offscreen targets; applications never issue draws from World data themselves. See [spatial APIs and tolerances](docs/spatial.md).

## Conventions

- C++20 in core/platform, Objective-C++ confined to the Metal backend.
- snake_case methods/variables; PascalCase classes.
- All rendering calls go through GraphicsDevice: explicit render passes inside Engine's frame, surface acquired only for presentation, resources destroyed through the device (never assume Metal retains them), and per-frame data (such as each view's instance array) uploaded with `upload_transient` rather than rewritten in a shared buffer. Draw instances through `plan_view_batches`/`plan_shadow_batches` (`draw_batches.hpp`, #1025): one instanced draw per mesh-material batch, never one draw per instance, and cull per pass, not at extraction (one snapshot serves every view and shadow map).
- Keep GPU struct layouts in `include/maya/renderer/shader_constants.hpp` and `include/maya/rhi/vertex.hpp` in step with the shader; Metal `float3` is 16 bytes, `packed_float3` is 12.
- Material assets (#1033) are edited through `material_properties()` like components, saved as material files version 2 (`material_file.hpp`; version 1 still loads), and published in memory with `AssetRegistry::publish`. In the editor, material edits are `SceneEditor` steps: never write a material into the registry or its file behind the open scene's back. The editor watches loaded material, texture, and environment files and the source images textures and environments name (`watched_files.cpp`); after writing or reloading one itself, call `note_watched_file` so the watcher does not take it for an outside change. Imported glTF files, their import files, and the files they name are watched too (`check_imported_sources`), and a changed one is imported again; importing in the editor is in `import_files.cpp` ([docs/editor.md](docs/editor.md#importing-models)). Meshes without tangents get MikkTSpace ones (`tangents.hpp`).
- Explicit CMake source lists keep runtime, editor, and sample dependencies separate.
- Native Metal state stays opaque to C++ consumers and uses ARC ownership.
- Use framebuffer pixel dimensions, not logical window size, for Metal and camera aspect. Input positions and UI layout are in points; convert with `WindowMetrics::scale()`.
- Editor input goes through `InputRouter`; never read held keys from the `Input` singleton in editor tools, or typing will leak into them.
- Runtime cleanup must not throw; application stop must tolerate partial initialization.

## Files

- `include/maya/core/application.hpp`: Content lifecycle boundary.
- `include/maya/core/engine.hpp`: Runtime session owner.
- `src/maya/platform/desktop_application.cpp`: Desktop loop.
- `samples/basic_scene/assets/`: Sample catalog, `basic.scene`, the material test scene `materials.scene`, the lights test scene `lights.scene` (#1034), meshes (including a UV sphere), material files (the original four at version 1; `spheres/` and `surfaces/` at version 2), textures (a tile grid, its normal map, a packed occlusion-roughness-metallic map, and a cutout), and two CC0 environments (`environments/`, Poly Haven HDRIs at 1k, the only committed HDR images).
- `resources/shaders/metal/renderer.metal`: Lit (physically based, with image-based lighting, point and spot lights, and shadows), shadow caster, sky, tone-map, debug, and presentation shaders.
- `resources/shaders/metal/editor_ui.metal`: Editor UI (Dear ImGui) shader, and the Assets panel's texture thumbnails.
- `resources/fonts/`: Inter and Geist Mono (SIL OFL) and Phosphor Light icons (MIT), licenses alongside, for the editor UI. Add icons as named constants in `apps/editor/editor_icons.hpp` so they enter the font atlas. Use the palette and helpers in `apps/editor/editor_theme.hpp` for new editor UI instead of raw ImGui colors.
- `apps/editor/`: Editor shell, UI renderer, input router, and editor camera.

FileSystem searches MAYA_RESOURCES, executable parents, and the working directory. A resource root for the sample contains both resources/ and samples/basic_scene/assets/. Failed resolution logs every candidate path.

CMake exports build/compile_commands.json; the root symlink supports clangd.
